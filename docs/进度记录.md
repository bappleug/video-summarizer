## 决策记录

- **D-001（2026-11-20）保留 `bili.py` 为核心资产，迁入 `tools/bili-subtitle/`，不归档。**
  理由：它解决了链路中最难的 B站登录态问题（扫码 + cookie 自动续期 + WBI 签名），两个候选开源项目均未处理好此点；且零依赖、带 18 个单测。原目录中它不是废弃物。

- **D-002（2026-11-20）交付形态：MVP = CLI + MCP Server；图形界面（Web/桌面）后置到 Phase 4。**
  理由：最终要对接多个 Agent（豆包等支持 MCP 的本地大模型 APP）和服务无编程基础的用户；MCP 是当前这些 APP 的通用集成协议，先留好接口，UI 阶段直接复用核心库。

- **D-003（2026-11-20）ASR 本地优先，云端按时长计费的专用 API 仅作低配设备降级。**
  理由：用户明确偏好本地小模型；调研确认云 ASR 为独立计费产品线（¥0.3~1.5/小时），并非对话模型的 token 费率，作为兜底成本可接受。

- **D-004（2026-11-20）总结/报告环节允许上云，走可配置的在线 LLM API。**
  理由：处理对象为公开发布的视频，内容无隐私顾虑；用户接受总结上云，主要顾虑的费率问题已被 D-003 的行情调研排除（总结每篇仅几千 token，成本可忽略）。

- **D-005（2026-11-20）设备兼容性为硬约束：本地 ASR 必须覆盖 Apple Silicon 与 Intel 两代 Mac。**
  理由：实际运行设备为混合 Mac 车队。MLX 系（如 mlx-whisper）仅支持 Apple Silicon；whisper.cpp、faster-whisper(CPU)、SenseVoice(onnx) 双端可跑。此约束直接限制引擎选型范围。

- **D-006（2026-11-20，用户拍板）本地 ASR 采用双引擎抽象：Apple Silicon = mlx-whisper large-v3-turbo；Intel = SenseVoice (sherpa-onnx int8) 多线程。**
  理由：research/01 实测 mlx 24× 实时、内存最低、专有名词最佳（仅 AS）；research/03 发现 SenseVoice 8 线程 100-150× 实时、模型仅 228MB、x86_64 官方支持（双端）。两者输出均为纯文本，抽象层成本极低。faster-whisper 出局（CPU 3.75×）。

- **D-007（2026-11-20，用户拍板）整体架构走自研整合路线：bili-subtitle 为核心，抽两 vendor 组件，管线编排/总结模块/MCP Server 自研。**
  抽件清单：VRA→小红书取材模块、B站 ai-zh protobuf 解析+字幕质检、报告 Skill 模板；BTC→MCP 11 工具设计、SenseVoice 多线程封装、三引擎适配器接口形状、短链安全重定向。理由：research/02/03 证明两 vendor 均无法整体满足（登录态/Intel/形态/依赖面）约束，而其组件质量高、 licences 友好（MIT）。

- **D-008（2026-11-20，用户拍板）放弃 Intel 本地 ASR：本地识别仅支持 Apple Silicon（mlx-whisper）；Intel 及其他设备一律走云端 API（硅基流动 SenseVoice，免费，research/04 §6 已实测）。**
  影响：①D-005 的「双端本地兼容」收敛为「AS 本地 + 其他云端」；②D-006 的本地 SenseVoice 后端退出 MVP（引擎抽象层保留，未来可按协议加回）；③「零 key 可用」收敛为仅 AS 机器成立，Intel 机器 ASR 需免费注册的硅基流动 key；④pyproject 不再需要 [sensevoice] extra，云端模块用 stdlib 实现（multipart 上传）。

- **D-009（2026-11-20，用户提出）Key 体验为一等需求：易配置 + 可诊断。**
  落地：`digest doctor`（三 key 实测体检/余额/端点 + 本地依赖 + 登录态）+ 运行时错误分类指引（401/402/403/429/超时 → 具体修法与控制台入口），硅基流动 401 自动试 `.cn`。进 S2 范围。

- **D-010（2026-11-20，用户提议+确认）引擎默认策略反转：云端为保底主路线，本地 mlx 降为可选插件。**

## Phase 1 记录（进行中）

### 2026-11-20 · ASR 基准完成 + 三个链路发现

**实测**：四引擎基准完成（见上方第 3 项与 research/01 报告），由 subagent 实施、主编排 agent 验收。SenseVoice 压缩包实际 999MB（此前 368MB 为下载中途误判），台账已修正。

**过程中的重要发现（影响后续设计）：**

1. **B站字幕接口存在风控污染**：登录态下快速连续请求，`subtitle_url` 会返回**随机无关视频的字幕**（实测拿到过笔记本维修、南大 vlog 等内容）。→ 管线设计必须加字幕内容健全性校验（与标题/简介相关性、重复率、语言一致性），不能盲信接口。
2. **cookie 自动续期疑似失效**：`correspond` 页面取不到 `refresh_csrf`，B站可能改了机制。当前凭据仍有效；一旦过期需用户重新扫码（届时升级为用户手动操作项）。bili-subtitle 的续期链路后续需要修复。
3. **网络约束**：hf.co 直连不通，模型下载需走 `HF_ENDPOINT=https://hf-mirror.com`；GitHub release 可直连。安装脚本/文档需内置此约定。

### 2026-11-20 · bili-transcriber 评估完成

- **SenseVoice 多线程是免费提速点**：`num_threads=min(8,…)` 时 311s 音频转写仅 2–3s（约 100–150× 实时），比我们 01 报告的单线程口径快一个量级（已回填 01 后记）。**这显著抬升「统一引擎 = SenseVoice」方案的性价比**，D-006 review 时一并考虑。

- B站匿名下载 bestaudio 可行（yt-dlp），与我们的 fetch_audio 路线互证。
